# EconomySystem 赚钱途径与动态委托规划

## 目标

为 EconomySystem 增加比“击杀直接发钱”更丰富、更可控的赚钱途径，让不同类型玩家都能通过正常 Minecraft 游戏行为参与经济，同时避免自动化农场无限制造货币、长期通胀和单一最优解。

本计划当前记录四个方向，其中：

- **P0 主线：动态委托 / 工作系统**
- **P0 主线：服务器回收站**
- **P2 备选：职业系统**
- **P2 备选：探索奖励**

当前开发重点优先放在前两项；职业与探索先保留设计接口，不要求第一阶段实现。

---

## 一、总体经济原则

### 1. 不把“执行动作”直接等同于“生成货币”

不建议新增以下类型的无限直接奖励：

```text
挖 1 个方块 -> +X 梦鱼币
收割 1 个作物 -> +X 梦鱼币
钓到 1 条鱼 -> +X 梦鱼币
砍 1 个木头 -> +X 梦鱼币
```

这类机制很容易被自动化农场转化为无限货币来源。

新的赚钱系统应优先采用：

- 有限需求；
- 周期刷新；
- 动态价格；
- 任务次数限制；
- 全服共享需求池或个人接单额度；
- 服务端权威结算。

### 2. 明确货币“水龙头”

动态委托与回收站属于真正向服务器经济中注入新梦鱼币的系统，因此必须具备总量控制能力。

玩家市场、求购单、玩家交易等仍主要承担玩家之间的货币流通，不应与系统注币逻辑混淆。

### 3. 优先复用现有系统

实现时优先复用当前已有能力：

- Economy 账户与流水；
- 系统商店物品与动态定价数据；
- 市场的 ItemStack / 订单匹配思路；
- 邮箱的离线通知与补偿能力；
- 现有服务端事件（击杀、玩家行为等）；
- UI 2 现有页面、列表、卡片、按钮与通知样式；
- 多版本 `common + target adapter` 架构。

不得为了新系统复制一套新的余额、物品快照、网络状态或持久化体系。

# 二、P0：动态委托 / 工作系统

## 2.1 核心定位

“委托中心”作为 EconomySystem 主要的主动赚钱入口。

玩家不是单纯重复某个动作获得钱，而是查看服务器当前需求，选择自己愿意完成的工作，再按委托规则领取报酬。

第一阶段建议支持的任务类型：

1. **物资提交委托**
   - 矿物；
   - 木材；
   - 农作物；
   - 食物；
   - 常见掉落物；
   - 建筑材料。

2. **猎杀委托**
   - 击杀指定生物一定数量；
   - 后续可扩展精英怪、Boss、特定维度目标。

其余复杂类型暂不进入首版。

## 2.2 示例

```text
矿业委托
铁锭 ×128
基础报酬：560
当前需求倍率：1.20
最终报酬：672 梦鱼币
全服剩余需求：512 / 1024
```

```text
猎人委托
击杀苦力怕 ×20
报酬：350 梦鱼币
今日剩余可完成次数：1
```

## 2.3 动态需求池

物资提交类委托建议使用“需求池”，而不是无限收购。

示例：

```text
今日铁锭需求：1024
今日小麦需求：4096
今日骨头需求：2048
```

玩家提交后扣减剩余需求。

需求接近满足时，可降低后续单价；需求长期未满足时，可以在下一刷新周期提高基础报酬或提高再次出现概率。

这样可以减少全服长期只刷同一种资源的问题。

## 2.4 动态价格建议

初版不需要设计复杂的真实市场模型，可以采用简单、可解释的倍率系统：

```text
最终单价 = 基础单价 × 需求倍率 × 稀缺倍率 × 活动倍率
```

建议：

- 所有倍率有明确上下限；
- 每次刷新变化幅度有限；
- 不允许因为历史数据异常把价格推到极端；
- 管理员配置中可以覆盖基础单价、最大需求、刷新权重和倍率区间。

后续可以考虑读取系统商店的价格历史作为参考值，但首版不要让两个动态价格系统互相无限反馈。

## 2.5 刷新机制

建议支持两层刷新：

### 日常委托

- 高频；
- 数量较多；
- 单次奖励较低；
- 以普通资源和普通生物为主。

### 周期 / 稀有委托

- 低频；
- 奖励较高；
- 资源需求更特殊；
- 后续可用于 Boss、稀有物品或探索内容。

实际刷新时间必须服务端记录，不能依赖客户端倒计时作为权威状态。

## 2.6 任务状态

建议至少包含：

```text
AVAILABLE   可接受 / 可提交
ACCEPTED    已接受
COMPLETED   已完成待结算或已结算
EXHAUSTED   全服需求已满足
EXPIRED     已过期
LOCKED      当前玩家不满足条件
```

对于纯物资提交任务，第一版可以允许“不提前接取，直接提交”，减少操作步骤。

猎杀、探索等需要持续记录进度的任务再采用显式接取。

## 2.7 UI 方向

建议新增一级页面：

```text
工作 / 委托中心
```

大致分区：

```text
┌────────────────────────────────────────────┐
│ 委托中心                         刷新倒计时 │
├──────────┬─────────────────────────────────┤
│ 全部     │ [矿业委托]                       │
│ 物资     │ 铁锭 ×128                        │
│ 猎杀     │ 672 梦鱼币                       │
│ 稀有     │ 剩余需求 512 / 1024              │
│          │ [提交]                           │
│          │                                  │
│          │ [猎人委托]                       │
│          │ 击杀苦力怕 ×20                   │
│          │ 350 梦鱼币                       │
└──────────┴─────────────────────────────────┘
```

建议显示：

- 委托名称；
- 目标图标；
- 数量 / 当前进度；
- 基础或最终报酬；
- 剩余服务器需求；
- 玩家今日完成次数；
- 刷新倒计时；
- 无法提交时的明确红色原因提示。

## 2.8 防滥用要求

必须服务端验证：

- 玩家实际拥有提交物品；
- NBT / 组件匹配规则；
- 数量；
- 委托是否仍有效；
- 全服需求是否仍有余额；
- 玩家个人次数限制；
- 猎杀目标是否由服务端事件记录；
- 重复网络包不能重复结算。

物品扣除和货币发放需要尽可能使用原子/事务式流程；发生错误时不得出现“物品未扣但钱已到账”或反过来的状态。

# 三、P0：服务器回收站

## 3.1 核心定位

回收站不是高收益赚钱方式，而是给大量低价值、过剩、容易堆积的资源提供一个**最低价值出口**。

其目标包括：

- 减少玩家直接把垃圾物品扔掉；
- 给普通生存行为提供少量额外收入；
- 为经济系统提供可控的小额注币渠道；
- 通过每日高价回收引导玩家改变当天的游戏目标。

## 3.2 基础回收

示例：

```text
腐肉 ×64 -> 6 梦鱼币
圆石 ×64 -> 2 梦鱼币
蜘蛛眼 ×64 -> 8 梦鱼币
海带 ×64 -> 4 梦鱼币
```

基础回收价格必须明显低于正常玩家市场的合理交易价格，防止回收站替代玩家市场。

## 3.3 每日高价回收

每个刷新周期随机选取若干物品进入高价回收：

```text
今日高价回收
骨头       +50%
铜锭       +30%
海带       +80%
```

高价回收仍然应该存在数量上限，例如：

```text
海带
今日剩余高价需求：1536
```

高价额度消耗完后：

- 可以恢复普通回收价；或
- 当日停止收购该物品。

具体策略做成配置项。

## 3.4 与动态委托的区别

两者不要做成同一个系统的两种皮肤。

### 委托中心

- 收益相对较高；
- 有明确目标；
- 有任务感和进度；
- 需要玩家主动选择；
- 可以包含击杀等非物品任务。

### 回收站

- 收益低；
- 操作快；
- 不需要接任务；
- 主要处理背包 / 仓库中的过剩物资；
- 重点是“垃圾也有一点价值”。

二者可以共享价格与需求基础设施，但业务语义和 UI 必须分开。

## 3.5 UI 方向

建议提供简单、快速的操作方式：

```text
┌─────────────────────────────────────────┐
│ 回收站                    今日高价回收  │
├──────────────────────┬──────────────────┤
│ 玩家背包             │ 当前选择         │
│ [ ][ ][ ][ ][ ][ ]   │ 腐肉 ×64         │
│ [ ][ ][ ][ ][ ][ ]   │                  │
│                      │ 预计获得：6       │
│                      │                  │
│                      │ [确认回收]        │
└──────────────────────┴──────────────────┘
```

可以考虑后续加入：

- 一键选择可回收物；
- 仅回收当前选中数量；
- 批量回收；
- 回收确认预览；
- 当日高价物品明显标识。

第一版不建议默认提供“自动回收背包所有匹配物品”，避免误操作。

## 3.6 回收价格来源

首版建议由独立配置控制，例如：

```text
itemId
baseRecyclePrice
maxDailyAmount
premiumWeight
premiumMultiplierRange
```

不要直接采用系统商店售价的固定百分比作为唯一规则，否则当系统商店动态价格异常时会把异常传播到回收系统。

后续可以允许配置：

```text
回收基准 = 固定配置 / 商店参考价 / 混合模式
```

# 四、P2 备选：职业系统

## 4.1 定位

职业系统暂不作为第一阶段赚钱来源，而更适合作为动态委托系统的长期成长层。

建议职业示例：

- 矿工；
- 农夫；
- 猎人；
- 渔夫；
- 商人。

## 4.2 不建议的设计

不要设计成：

```text
矿工职业 -> 每挖一个矿直接加钱
农夫职业 -> 每收一个作物直接加钱
```

否则职业系统会再次变成自动化印钞机。

## 4.3 推荐设计

职业主要提供：

- 职业经验；
- 职业等级；
- 解锁更高级委托；
- 提高每日可接委托数量；
- 解锁特殊任务池；
- 小幅提升对应委托的报酬上限；
- 职业称号 / 展示信息。

职业经验主要来自**完成对应类型委托**，而不是直接统计每一次普通动作。

## 4.4 与主线的关系

因此职业系统应建立在动态委托已经稳定以后：

```text
玩家行为
   ↓
完成委托
   ↓
获得梦鱼币 + 职业经验
   ↓
职业升级
   ↓
解锁更高级委托
```

第一阶段仅要求动态委托的数据模型保留可扩展的 `category / profession requirement / profession xp reward` 一类字段即可，不需要立即实现职业 UI 和持久化。

# 五、P2 备选：探索奖励

## 5.1 定位

探索奖励用于鼓励玩家离开固定生产区、主动跑图，并给不喜欢刷资源或战斗的玩家提供另一种收益来源。

它更适合作为低频、一次性或周期性奖励，而不是无限重复赚钱方式。

## 5.2 可考虑的任务

### 一次性里程碑

示例：

```text
首次进入末地
首次进入下界
首次发现特定结构
首次到达距离出生点一定范围之外
首次完成特定探索成就
```

### 周期探索委托

示例：

```text
本周探索目标：发现一个蘑菇岛
奖励：1200 梦鱼币
```

```text
探索距离出生点 5000 格以外的新区域
奖励：600 梦鱼币
```

## 5.3 防刷原则

不能单纯相信客户端报告“我发现了某结构”。

需要尽可能通过服务端可验证数据完成判定，例如：

- 服务端玩家位置；
- 维度切换事件；
- 原版 advancement / criterion；
- 服务端结构查询；
- 每玩家已领取记录；
- 每周期任务唯一 ID。

对于实现成本过高、难以可靠验证的探索目标，不进入首版。

## 5.4 与委托中心整合

如果未来实现，探索任务优先作为“委托中心”的一种任务分类，而不是再做完全独立的任务框架。

即：

```text
委托中心
├── 物资
├── 猎杀
├── 探索（后续）
└── 稀有 / 周常（后续）
```

# 六、建议实施顺序

## Phase 1：通用需求与结算基础

建立 loader-neutral 的公共模型：

- `JobDefinition`；
- `JobInstance`；
- `JobCategory`；
- `JobProgress`；
- `DemandPool`；
- `RewardQuote`；
- 刷新策略；
- 需求倍率；
- 结算结果；
- 服务端持久化接口。

同时设计回收站可共享的：

- 动态需求；
- 配额；
- 价格报价；
- 刷新周期。

不要让 UI 或 NeoForge 类进入核心业务模型。

## Phase 2：回收站 MVP

优先实现简单可验证的物品回收：

1. 配置回收物品；
2. 服务端报价；
3. 服务端验证背包；
4. 扣除物品；
5. 发放梦鱼币；
6. 流水记录；
7. 每日高价回收；
8. 总量 / 配额限制；
9. UI。

回收站适合作为动态需求与报价基础设施的第一块落地业务。

## Phase 3：物资动态委托 MVP

实现：

- 委托生成；
- 委托刷新；
- 物品提交；
- 全服需求池；
- 玩家完成次数；
- 动态报价；
- UI；
- 管理员配置与调试入口。

## Phase 4：猎杀委托

复用现有实体死亡事件，增加玩家任务进度记录。

需要特别处理：

- 击杀归属；
- 非玩家击杀；
- 自动化陷阱；
- 同一实体重复事件；
- 任务过期后的进度失效。

## Phase 5：稳定后再评估 P2

在动态委托和回收站经过实际服务器经济数据验证后，再决定：

- 是否加入职业等级；
- 是否加入探索分类；
- 是否增加周常 / 稀有委托；
- 是否把系统商店价格历史纳入需求算法。

# 七、管理与配置要求

管理员至少需要能够配置：

- 功能总开关；
- 可生成委托的物品 / 生物白名单；
- 基础奖励；
- 需求数量范围；
- 单周期出现权重；
- 玩家完成次数限制；
- 全服总需求；
- 刷新周期；
- 动态倍率最小 / 最大值；
- 回收物品与基础回收价；
- 高价回收数量；
- 高价倍率范围；
- 是否允许普通价格继续回收；
- 调试 / 强制刷新能力。

所有配置 reload 后应尽可能安全生效；已有委托实例是否立即受新配置影响必须提前定义，避免刷新后奖励被意外改变。

推荐：**已生成实例保存自己的结算快照，新配置只影响下一批生成的委托。**

# 八、审计与流水

所有系统发钱必须进入现有 Economy 流水 / Ledger，并使用明确来源，例如：

```text
economysystem:job_reward
economysystem:recycle_reward
economysystem:exploration_reward
```

日志建议包含：

- 玩家 UUID；
- 委托 / 回收批次 ID；
- 物品或目标；
- 数量；
- 实际奖励；
- 动态倍率；
- 服务端时间；
- 刷新周期 ID。

这样后续才能分析系统到底向服务器注入了多少货币，并调整经济参数。

# 九、当前决策摘要

当前确定：

1. **优先实现动态委托 / 工作系统。**
2. **优先实现服务器回收站。**
3. 职业系统保留为委托系统的长期成长层，暂不作为近期主功能。
4. 探索奖励保留为未来委托分类，暂不独立建设另一套任务框架。
5. 新系统必须限制无限货币生成，优先使用需求池、周期刷新、数量上限和动态报价。
6. 物资委托与回收站可以共享需求 / 报价基础设施，但必须保持不同业务语义和 UI。
7. 所有物品扣除、任务验证和货币结算必须服务端权威。
8. 实现需继续遵循现有 `common + target adapter` 多版本架构。
