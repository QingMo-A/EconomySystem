# EconomySystem 赚钱途径与动态委托规划

## 目标

为 EconomySystem 增加比“击杀直接发钱”更丰富、更可控的赚钱途径，让不同类型玩家都能通过正常 Minecraft 游戏行为参与经济，同时避免自动化农场无限制造货币、长期通胀和单一最优解。

本计划当前记录四个方向，其中：

- **P0 主线：动态委托 / 工作系统**
- **P0 主线：服务器回收站**
- **P2 备选：职业系统**
- **P2 备选：探索奖励**

当前开发重点优先放在前两项；职业与探索先保留设计接口，不要求第一阶段实现。

其中动态委托系统采用明确的“题库式”设计：

> **管理员维护委托库，系统只负责从合法模板中抽取、组合、计算并生成实际委托。**

系统不应无约束地凭空随机创造任务。

---

# 一、总体经济原则

## 1.1 不把普通动作直接等同于生成货币

不建议新增以下无限直接奖励：

```text
挖 1 个方块 -> +X 梦鱼币
收割 1 个作物 -> +X 梦鱼币
钓到 1 条鱼 -> +X 梦鱼币
砍 1 个木头 -> +X 梦鱼币
```

这类机制极易被自动化农场转化为无限货币来源。

新的赚钱系统优先采用：

- 有限需求；
- 周期刷新；
- 单条委托过期；
- 动态价格；
- 全服配额或个人配额；
- 服务端权威结算；
- 管理员可配置的委托库。

## 1.2 明确货币“水龙头”

动态委托与回收站会真正向服务器经济中注入新的梦鱼币，因此必须具备总量控制能力。

玩家市场、求购单、玩家交易等则主要承担玩家之间的货币流通，不应与系统注币逻辑混淆。

## 1.3 优先复用现有系统

实现时优先复用 EconomySystem 当前已有能力：

- Economy 账户与流水；
- 系统商店物品与动态定价数据；
- 市场的 ItemStack / 订单匹配与事务思路；
- 邮箱的离线通知与补偿能力；
- 现有服务端事件，例如实体死亡；
- UI 2 现有页面、列表、卡片、按钮与通知样式；
- 现有 `common + target adapter` 多版本架构。

不得为了委托系统复制一套新的余额、物品快照、网络状态或平台专属业务模型。

---

# 二、P0：动态委托 / 工作系统

## 2.1 核心定位

“委托中心”作为 EconomySystem 的主要主动赚钱入口。

玩家不是重复某个动作就自动获得货币，而是查看当前委托，根据服务器需求选择任务，通过提交物资、猎杀目标或未来其他行为获得报酬。

第一阶段重点支持：

1. **物资提交委托**
   - 矿物；
   - 木材；
   - 农作物；
   - 食物；
   - 常见掉落物；
   - 建筑材料。

2. **猎杀委托**
   - 击杀指定生物一定数量；
   - 后续可扩展精英怪、Boss、特定维度目标。

探索、职业、活动等内容后续继续建立在同一 Commission 框架上。

---

# 三、委托库：题库式程序化生成

## 3.1 基本思想

管理员创建的不是每一次玩家看到的最终任务，而是用于生成任务的“题库”。

整体过程：

```text
管理员维护委托库
        ↓
选择委托模板
        ↓
选择合法委托人
        ↓
选择合法目标
        ↓
生成数量
        ↓
计算奖励
        ↓
校验组合合法性
        ↓
生成并冻结 CommissionInstance
```

这样可以同时做到：

- 保持随机性；
- 保持管理员控制；
- 避免荒谬组合；
- 方便数据包式扩展；
- 方便兼容其他模组物品；
- 为职业、探索、公共建设、节日活动等后续功能保留统一框架。

## 3.2 核心对象

第一版建议围绕以下对象建模：

```text
CommissionTemplate
CommissionRequester
CommissionTargetPool
CommissionInstance
CommissionBatch
PersonalCommissionBatch
```

语义分别为：

- `CommissionTemplate`：题型 / 委托模板；
- `CommissionRequester`：委托人；
- `CommissionTargetPool`：可抽取目标池；
- `CommissionInstance`：最终生成的实际委托；
- `CommissionBatch`：公共委托批次；
- `PersonalCommissionBatch`：某名玩家独立的个人委托批次。

---

# 四、CommissionTemplate：委托模板

模板负责定义一类委托可以如何生成。

例如：

```text
模板：矿产供应委托

类型：ITEM_DELIVERY
委托人池：mining_requesters
目标池：basic_mining_materials
数量：64 ~ 256
步长：32
奖励：基础价值 × 数量 × 0.9~1.3
权重：100
```

模板应至少能够控制：

- 唯一 ID；
- 委托类型；
- 公共 / 个人可用性；
- 委托人池；
- 目标池；
- 数量范围；
- 数量步长；
- 奖励算法；
- 出现权重；
- 稀有度 / 分类；
- 需求上限；
- 玩家提交上限；
- 过期规则；
- 文本模板；
- 特殊条件；
- 未来职业条件；
- 是否允许跨批次继续存在。

首版不要求所有字段都进入 UI，但数据模型应避免把后续扩展写死。

---

# 五、CommissionRequester：委托人

## 5.1 委托人不只是显示名称

委托人可以拥有自己的经济特征和生成约束。

例如：

```text
城镇铁匠铺

允许类别：
- iron
- coal
- copper

需求量倍率：0.8
奖励倍率：1.05
稀有度：普通
```

```text
皇家军需处

需求量倍率：2.5
奖励倍率：1.15
出现概率：较低
特点：大量收购物资
```

```text
神秘收藏家

允许目标：稀有物品
需求量：低
奖励：高
出现概率：极低
```

因此不同委托人不只是换一个名字，而是可以形成一定辨识度。

## 5.2 委托人池

模板不应直接绑定全局所有委托人，而是引用合法委托人池，例如：

```text
mining_requesters
├── 城镇铁匠铺
├── 北方矿业协会
└── 皇家军需处
```

这样可以避免：

```text
渔夫要求钻石块
农夫要求下界合金
铁匠要求河豚
```

除非管理员明确创建特殊模板允许这种组合。

# 六、CommissionTargetPool：目标池

目标池负责定义系统可以从哪些目标中抽取。

例如：

```text
basic_mining_materials
├── minecraft:iron_ingot
├── minecraft:copper_ingot
├── minecraft:coal
└── minecraft:gold_ingot
```

```text
basic_crops
├── minecraft:wheat
├── minecraft:carrot
├── minecraft:potato
└── minecraft:beetroot
```

后续应考虑支持：

- Minecraft Item ID；
- Minecraft Tag；
- EconomySystem 自定义目标池；
- 兼容其他模组注册物品；
- 猎杀类型的 EntityType 目标池；
- 后续探索类型的结构 / 群系 / advancement 目标。

例如：

```text
#minecraft:logs
```

或：

```text
economysystem:commission/mining_common
```

# 七、CommissionInstance：实际委托

## 7.1 生成后必须冻结

系统从模板中抽取后，生成 `CommissionInstance`。

例如：

```text
模板：矿产供应委托

抽中委托人：城镇铁匠铺
抽中目标：铁锭
生成数量：160
奖励倍率：1.12
```

最终实例：

```text
【城镇铁匠铺的物资委托】

铁锭 ×160
奖励：1260 梦鱼币
```

实例生成后，应保存自己的结算快照。

假设 12:00 生成：

```text
铁锭 ×128
奖励 960
```

即使 12:05 系统商店价格发生变化，该委托仍然必须保持：

```text
铁锭 ×128
奖励 960
```

不能在提交时重新按照最新市场价格计算，否则会造成：

- UI 与实际结算不一致；
- 玩家等待价格刷新套利；
- 不同时间提交同一委托得到不同结果；
- 配置 reload 后旧任务奖励突变。

## 7.2 实例建议字段

至少包括：

```text
commissionId
batchId
templateId
requesterId
type
targetSnapshot
requiredAmount
remainingAmount
rewardSnapshot
generatedAt
expiresAt
status
persistentAcrossRefresh
```

个人委托还需关联：

```text
ownerPlayerUuid
progress
```

# 八、公共委托与个人委托

委托系统第一版架构就应明确支持两种委托池，避免后续再拆持久化、协议和生成器。

## 8.1 公共委托

公共委托由全服共享。

所有玩家看到：

- 相同委托；
- 相同剩余需求；
- 相同过期时间；
- 相同刷新时间；
- 相同完成 / 耗尽状态。

例如：

```text
第 218 期公共委托

城镇建设局
玻璃 ×1000
当前已提交：743 / 1000
奖励：9 梦鱼币 / 个
过期：02:13:42
```

这种委托适合：

- 大宗物资收购；
- 全服资源需求；
- 公共建设；
- 大型猎杀目标；
- 节日活动。

## 8.2 个人委托

每名玩家拥有独立的 `PersonalCommissionBatch`。

不同玩家：

- 抽到的委托不同；
- 委托目标不同；
- 数量可能不同；
- 奖励可能不同；
- 当前进度不同；
- 下一次刷新时间不同。

例如：

```text
玩家 A
├── 铁锭 ×64
├── 击杀骷髅 ×12
└── 胡萝卜 ×128
```

```text
玩家 B
├── 铜锭 ×96
├── 击杀僵尸 ×20
└── 云杉原木 ×192
```

个人委托的目的之一就是避免全服在同一刷新时刻争抢同一种最优资源。

## 8.3 个人委托槽

建议每轮个人委托保持较少数量，避免玩家只从十几条任务中机械挑选收益最高的两条。

例如：

```text
普通委托：3 个
稀有委托：1 个
特殊委托：0~1 个
```

整体约 4~5 条。

这应该做成管理员配置，而不是硬编码。

# 九、刷新系统

## 9.1 刷新时间与过期时间必须分离

系统中两个时间概念不能混淆。

### `nextRefreshAt`

表示：

> 什么时候生成下一批委托？

### `expiresAt`

表示：

> 某一条具体委托还能存在多久？

因此同一批次中的不同任务可以拥有不同过期时间。

例如：

```text
个人下一轮刷新：04:13:28

铁匠紧急订单
过期：00:47:12

农场主长期采购
过期：03:26:40
```

## 9.2 公共委托刷新

公共委托可以使用统一批次：

```text
CommissionBatch
├── batchId
├── generatedAt
├── nextRefreshAt
└── commissions[]
```

例如默认每 6 小时刷新一次。

所有玩家看到相同的刷新倒计时。

第一版允许使用单一公共刷新组；后续如有需要再扩展：

```text
normal
rare
daily
event
```

不同刷新组使用不同周期。

## 9.3 个人委托刷新

个人委托必须使用每玩家独立的刷新时间。

```text
PersonalCommissionBatch
├── playerUuid
├── batchId
├── generatedAt
├── nextRefreshAt
└── commissions[]
```

不能所有玩家都在固定整点同步刷新。

建议采用：

```text
baseInterval + 小范围 jitter
```

例如：

```text
基础刷新：4h
随机偏移：±30m
```

则不同玩家可能得到：

```text
A：3h47m
B：4h18m
C：4h03m
```

这样可以：

- 让每个人刷新节奏有所不同；
- 避免所有玩家同一时刻集中请求；
- 避免服务器同时为大量玩家生成任务；
- 避免统一刷新导致资源行为过度集中。

随机范围必须保持合理，不能出现一个玩家 2 小时刷新、另一个玩家 12 小时刷新这种明显不公平情况。

## 9.4 使用绝对服务端时间

刷新不应依赖客户端倒计时，也不建议仅使用服务器 tick 累加。

持久化：

```text
nextRefreshAt
expiresAt
```

使用服务端绝对时间。

例如服务器关服期间时间仍正常推进：

```text
16:00 关服
nextRefreshAt = 18:00
20:00 再开服
```

服务器发现当前时间已经超过 `nextRefreshAt`，则旧批次失效，并按规则生成新批次。

这样玩家无法通过服务器离线或不开 GUI 延长委托寿命。

## 9.5 不能以“打开 GUI”开始计时

个人委托的生命周期由服务端持久化状态决定，而不是玩家何时第一次打开委托页面。

否则玩家可以长期不打开 GUI，在需要赚钱时再打开，从而人为延后完整任务周期。

正确逻辑：

```text
玩家已有 PersonalCommissionBatch
        ↓
服务端持久化 nextRefreshAt
        ↓
时间正常流逝
        ↓
玩家下次上线 / 请求委托数据
        ↓
若当前时间 >= nextRefreshAt
        ↓
废弃旧批次并生成新批次
```

# 十、单条委托过期

## 10.1 每条 CommissionInstance 独立过期

模板能够配置有效期，例如：

```text
普通委托：2~4h
紧急委托：20~60min
稀有委托：1~2h
长期委托：持续到本批次结束
```

这样可以生成：

```text
【紧急委托】
皇家军需处急需铁锭

铁锭 ×128
奖励：1240 梦鱼币
有效期：37 分钟
```

紧急、高收益、短有效期的委托可以给玩家带来真正的取舍。

## 10.2 普通委托不得无限跨批次堆积

默认规则：

```text
effectiveEndAt = min(expiresAt, nextRefreshAt)
```

即普通委托最多存活到所属批次结束。

例如：

```text
下一轮个人刷新：4 小时后
任务自身有效期配置：8 小时
```

实际仍只存活 4 小时。

否则会出现：

```text
上一轮剩余任务
+
下一轮新任务
+
下下一轮任务
```

导致委托不断堆积。

## 10.3 特殊任务允许跨批次

部分特殊委托可以配置：

```text
persistentAcrossRefresh = true
```

适用于：

- 剧情任务；
- 节日活动；
- 管理员手动发布任务；
- 大型公共建设；
- 长周期活动。

此时主要依赖自己的 `expiresAt` 或管理员结束条件，不受普通批次刷新直接删除。

# 十一、委托结算模式

不同类型委托的结算方式不应强行统一。

## 11.1 公共物资提交型

适合按实际提交量即时结算。

例如：

```text
总需求：160 铁锭
玩家提交：32
```

立即：

- 扣除 32 铁锭；
- 按冻结单价发放对应奖励；
- 全服剩余需求减少 32；
- 记录玩家贡献。

即使整个委托最终没有在过期前完成，已经提交的物资和已经结算的奖励不会回滚。

## 11.2 个人完成型

例如：

```text
击杀僵尸 13 / 20
```

应在完整达到目标后一次性结算。

如果任务过期：

```text
13 / 20
→ EXPIRED
```

不继续累计到下一轮。

## 11.3 未来公共大型任务

公共建设类可以进一步支持：

```text
个人贡献奖励
+
阶段奖励
+
最终全服完成奖励
```

但不要求第一版全部实现。

---

# 十二、委托状态

建议至少包含：

```text
AVAILABLE   可参与 / 可提交
ACTIVE      已接取并记录个人进度
COMPLETED   已完成
EXHAUSTED   公共需求已被完全满足
EXPIRED     已过期
DISABLED    被管理员禁用或模板失效
LOCKED      当前玩家不满足参与条件
```

纯物资提交类可以允许不显式接取，直接提交。

猎杀、探索等需要持续记录进度的任务可使用 `ACTIVE`。

状态的最终权威始终在服务端。

---

# 十三、生成规则与分类配额

不建议每轮简单从所有模板中完全随机抽 N 条。

更适合使用“分类配额 + 分类内权重抽取”。

例如公共批次生成 8 条：

```text
基础物资：3
农业：1
猎杀：2
特殊需求：1
稀有：1
```

个人批次例如：

```text
普通：3
稀有：1
特殊：0~1
```

分类内部再根据模板权重抽取。

这样管理员可以稳定控制服务器整体经济方向，而不是因为随机数导致某一轮全部都是矿业委托。

---

# 十四、固定委托与随机模板

系统应同时支持：

## 14.1 程序化随机模板

例如：

```text
矿业协会随机收购一种矿产
数量随机
奖励倍率随机
```

适合日常委托。

## 14.2 固定委托

例如：

```text
皇家军需处
铁锭 ×512
固定奖励：5000 梦鱼币
```

适合：

- 服务器活动；
- 剧情；
- 临时资源调控；
- 节日活动；
- 管理员手动发布。

## 14.3 公共建设委托

后续可以扩展：

```text
【城镇扩建计划】

石砖：6821 / 10000
铁锭：2031 / 3000
玻璃：4100 / 5000
```

由全服共同贡献。

---

# 十五、奖励计算

建议至少支持以下几种奖励方式。

## 15.1 固定奖励

```text
reward = 500
```

## 15.2 固定单价

```text
奖励 = 单价 × 实际数量
```

## 15.3 动态价值模式

可以参考：

- 管理员配置基础价格；
- 系统商店基准价；
- 当前需求；
- 委托人倍率；
- 模板倍率；
- 活动倍率。

例如：

```text
最终价值
=
基础价值
× 数量
× 模板倍率
× 委托人倍率
× 需求倍率
× 随机浮动
```

所有倍率必须：

- 有明确上下限；
- 刷新变化幅度有限；
- 不允许异常历史数据将价格推到极端。

系统商店和委托动态价格首版不要形成双向无限反馈。

最终奖励在 `CommissionInstance` 生成时冻结。

# 十六、需求限制与防通胀

物资委托建议支持：

```text
globalLimit
playerLimit
```

例如：

```text
全服铁锭需求：512
单玩家最多贡献：128
```

这样既限制系统注币，也避免自动化程度最高的一名玩家瞬间吃完全部公共委托。

个人委托则通过：

- 委托槽数量；
- 刷新周期；
- 单条过期；
- 每批次奖励上限；
- 难度与奖励区间；

控制总注币量。

后续可以统计每个批次实际注币量，为管理员提供经济调参依据。

# 二十一、P0：服务器回收站

## 21.1 核心定位

回收站不是高收益赚钱方式，而是给低价值、过剩、容易堆积的资源提供一个**最低价值出口**。

目标：

- 减少玩家直接丢弃垃圾资源；
- 给普通生存行为提供少量额外收入；
- 提供可控的小额注币渠道；
- 通过周期高价回收引导玩家改变短期目标。

## 21.2 基础回收

例如：

```text
腐肉 ×64 -> 6 梦鱼币
圆石 ×64 -> 2 梦鱼币
蜘蛛眼 ×64 -> 8 梦鱼币
海带 ×64 -> 4 梦鱼币
```

基础回收价必须明显低于正常玩家市场的合理交易价格，避免回收站取代玩家市场。

## 21.3 周期高价回收

每个刷新周期从管理员配置的回收库中抽取若干物品：

```text
本期高价回收
骨头 +50%
铜锭 +30%
海带 +80%
```

每种高价回收仍应存在数量上限：

```text
海带
剩余高价需求：1536
```

额度耗尽后可以配置为：

- 恢复普通回收价；或
- 本周期停止收购该物品。

## 21.4 与委托系统的区别

### 委托中心

- 收益更高；
- 有明确目标；
- 有委托人和任务感；
- 有刷新、过期、进度；
- 可以支持物资、猎杀、探索等多种行为。

### 回收站

- 收益低；
- 操作快；
- 不要求接取任务；
- 主要清理仓库 / 背包过剩资源；
- 核心语义是“垃圾也有一点最低价值”。

两者可以共享：

- 报价基础设施；
- 动态需求；
- 配额；
- 流水记录；
- 服务端事务组件。

但业务和 UI 必须保持分离。

## 21.5 回收 UI

```text
┌─────────────────────────────────────────┐
│ 回收站                    本期高价回收  │
├──────────────────────┬──────────────────┤
│ 玩家背包             │ 当前选择         │
│ [ ][ ][ ][ ][ ][ ]   │ 腐肉 ×64         │
│ [ ][ ][ ][ ][ ][ ]   │                  │
│                      │ 预计获得：6       │
│                      │                  │
│                      │ [确认回收]        │
└──────────────────────┴──────────────────┘
```

第一版不建议默认提供“自动回收背包全部匹配物品”，避免误操作。

后续可增加：

- 批量选择；
- 指定数量；
- 高价标识；
- 一键选择可回收物；
- 回收确认预览。

## 21.6 回收报价来源

第一版建议独立配置：

```text
itemId
baseRecyclePrice
maxAmountPerCycle
premiumWeight
premiumMultiplierRange
```

不要简单固定为系统商店售价的某个百分比，否则商店价格异常会传播到回收系统。

后续可支持：

```text
固定配置 / 商店参考价 / 混合模式
```

# 二十二、P2 备选：职业系统

## 22.1 定位

职业系统不作为第一阶段的直接发钱来源，而应作为委托系统的长期成长层。

例如：

- 矿工；
- 农夫；
- 猎人；
- 渔夫；
- 商人。

## 22.2 推荐关系

```text
完成委托
    ↓
获得梦鱼币 + 职业经验
    ↓
职业升级
    ↓
解锁高级委托 / 特殊委托池
```

而不是：

```text
挖矿 -> 直接发钱
```

第一版 CommissionTemplate 可以提前预留：

```text
requiredProfession
requiredProfessionLevel
professionExperienceReward
```

但不要求立即实现职业持久化和职业 UI。

## 22.3 未来个人委托个性化

职业系统稳定后，个人委托可以根据玩家发展方向调整权重，但不能完全锁死玩家玩法。

例如：

```text
60~70%：符合玩家职业或近期发展方向
30~40%：从其他合法委托中随机生成
```

这样既能体现个性化，又不会让矿工玩家永远只看到矿业任务。

---

# 二十三、P2 备选：探索奖励

## 23.1 定位

探索奖励鼓励玩家离开固定生产区并主动跑图，为不喜欢刷资源或战斗的玩家提供低频赚钱方式。

优先作为：

```text
CommissionType.EXPLORATION
```

而不是再开发一套独立任务框架。

## 23.2 示例

```text
探索蘑菇岛
发现一个新的蘑菇岛群系
奖励：1200 梦鱼币
```

```text
寻找林地府邸
奖励：1800 梦鱼币
```

或一次性里程碑：

```text
首次进入末地
首次进入下界
首次发现指定结构
首次抵达距出生点一定距离
```

## 23.3 服务端验证

尽量依赖：

- 服务端玩家位置；
- 维度切换事件；
- advancement / criterion；
- 服务端结构查询；
- 每玩家完成记录；
- 每周期唯一委托 ID。

不能单纯接受客户端上报“我找到了某结构”。

实现成本过高且难以可靠验证的目标不进入首版。

---

# 二十四、防滥用与事务要求

所有提交和结算必须由服务端验证：

- 玩家实际拥有提交物品；
- NBT / Data Component 匹配；
- 数量；
- CommissionInstance 是否仍存在；
- 当前时间是否已经过期；
- 所属批次是否仍有效；
- 全服剩余需求；
- 玩家个人提交额度；
- 猎杀进度是否由服务端事件记录；
- 重复网络包不得重复结算。

物品扣除和货币发放应使用事务式流程。

不得出现：

```text
物品没扣但钱到账
```

或：

```text
物品扣掉但奖励失败且无法恢复
```

网络请求应具有幂等或一次性状态保护。

建议来源：

```text
economysystem:commission_reward
economysystem:recycle_reward
economysystem:exploration_reward
```

日志建议保存：

- 玩家 UUID；
- commissionId；
- batchId；
- templateId；
- requesterId；
- 目标；
- 数量；
- 实际奖励；
- 奖励倍率；
- 服务端时间；
- 公共 / 个人类型。

这样管理员之后可以统计：

- 每轮总注币；
- 最受欢迎的委托；
- 完成率；
- 平均过期率；
- 各资源被系统吸收的数量；
- 回收站注币占比。

这些数据将直接用于经济参数调整。

# 二十七、当前设计决策摘要

目前确定：

1. **动态委托 / 工作系统为 P0 主线。**
2. **服务器回收站为 P0 主线。**
3. 职业系统作为 P2 备选成长层，不采用“普通动作直接发钱”。
4. 探索奖励作为 P2 备选，未来优先整合进 Commission 框架。
5. 委托采用“管理员委托库 + 系统程序化生成”模式。
6. 核心题库对象为 `CommissionTemplate / CommissionRequester / CommissionTargetPool`。
7. 最终任务使用不可随外部价格变化的 `CommissionInstance` 快照。
8. 第一版架构同时支持**公共委托**和**个人委托**。
9. 公共委托全服共享任务、需求与刷新时间。
10. 个人委托每名玩家拥有独立任务内容、进度和 `nextRefreshAt`。
11. 个人刷新使用“基础周期 + 小范围 jitter”，避免所有玩家同步刷新且保持公平。
12. 每条委托拥有独立 `expiresAt`。
13. 刷新时间与过期时间是两个独立概念。
14. 普通委托默认 `effectiveEndAt = min(expiresAt, nextRefreshAt)`，不得无限跨批次堆积。
15. 特殊任务可通过 `persistentAcrossRefresh` 跨批次存在。
16. 刷新与过期均由服务端绝对时间管理，不因关服、离线或不开 GUI 而暂停。
17. 已生成任务的奖励、目标和数量保存快照；配置 reload 只影响未来生成任务。
18. 公共提交型物资委托可按实际提交数量即时结算。
19. 个人进度型任务在完整完成后结算，过期后旧进度失效。
20. 已完成 / 已耗尽任务默认等待下一轮刷新，不立即无限补新任务。
21. 委托使用分类配额 + 分类内权重，而不是全局无约束随机。
22. 系统同时支持程序化随机模板与管理员固定委托。
23. 所有物品扣除、任务进度、过期、刷新和奖励结算必须服务端权威。
24. 回收站和委托可以共享需求 / 报价 / 事务基础设施，但 UI 与业务语义保持独立。
25. 所有系统注币进入 Economy Ledger，后续可依据实际数据调节经济参数。
