# EconomySystem 委托奖励邮件结算补充计划

> 本文是 `plans/earning-paths-and-dynamic-jobs-plan.md` 的约束性补充设计，主要定义委托及未来奖励型玩法如何通过邮箱完成最终结算。

## 一、核心决策

EconomySystem 后续新增的“奖励型收入”统一采用：

```text
完成目标
   ↓
服务端确认完成
   ↓
生成奖励结算记录
   ↓
发送系统奖励邮件
   ↓
玩家进入邮箱
   ↓
领取奖励附件
   ↓
最终到账
```

玩家完成委托后，**不得直接把梦鱼币加到账户余额**。

委托中心只负责告诉玩家：

```text
委托已完成
奖励已发送至邮箱
```

真正的奖励领取统一发生在邮箱系统中。

设计目的：

- 增强委托完成后的沉浸感；
- 强化玩家对 EconomySystem 邮箱系统的认知；
- 让邮箱成为经济系统中真正重要的“结算中心”；
- 统一离线奖励、活动奖励、补偿奖励、委托奖励等发放路径；
- 未来可以在奖励邮件中加入委托人文本、事件说明和特殊附件，而不是只有一个余额变化提示。

---

# 二、适用范围

以下属于“奖励型收入”，原则上统一发送至邮箱：

- 个人物资委托奖励；
- 个人猎杀委托奖励；
- 公共委托贡献奖励；
- 公共委托阶段奖励；
- 公共委托最终完成奖励；
- 未来探索委托奖励；
- 未来职业任务奖励；
- 节日 / 活动委托奖励；
- 剧情委托奖励；
- 管理员发布的特殊委托奖励；
- 未来其他明确属于“任务 / 奖励”的收入。

以下不强制走奖励邮件，因为其语义是“交易结算”而非“奖励”：

- 玩家市场成交；
- 玩家转账；
- 系统商店购买 / 出售结算；
- 回收站出售所得；
- 其他明确的即时交易行为。

因此原则是：

```text
Reward -> Mailbox
Trade / Transfer -> Immediate settlement
```

如果未来需要让某一种交易也通过邮箱结算，应单独设计，不与本规则混淆。

---

# 三、奖励邮件不是普通通知邮件

委托奖励邮件必须具有可领取的“奖励附件”，而不是：

```text
邮件通知
   ↓
系统早已偷偷把钱加到账户
```

这种方式虽然看起来经过邮箱，但玩家实际上没有通过邮箱领取奖励，无法达到强化邮箱系统存在感的目的。

正确模型应为：

```text
Commission completed
       ↓
CommissionRewardRecord
       ↓
Reward Mail
       ↓
Currency / Item reward attachment
       ↓
Player claims
       ↓
Economy account / inventory changes
```

即：**领取邮件附件本身就是最终结算动作。**

---

# 四、邮箱需要支持货币奖励附件

当前委托主要奖励为梦鱼币，因此邮箱系统需要支持一种正式的货币奖励附件能力。

建议抽象为：

```text
MailAttachment
├── ItemAttachment
└── CurrencyAttachment
```

或保持当前附件模型的兼容方式，新增等价的：

```text
MailCurrencyGrant
```

首版只需要支持 EconomySystem 当前单一货币“梦鱼币”。

建议字段：

```text
currencyId
a mount / amount
source
reason
rewardRecordId
```

实际实现时字段名以现有邮箱 / API 架构为准，不要求机械照搬上述名称。

### 领取货币附件

玩家点击领取后：

```text
校验邮件存在
   ↓
校验附件未领取
   ↓
校验 rewardRecordId 未结算
   ↓
原子增加余额
   ↓
写 Economy Ledger
   ↓
标记附件已领取
```

任何重复网络包、重新登录、客户端重复点击都不能重复领取。

---

# 五、奖励记录与邮件必须解耦

不要只依赖“邮件里有一个 1260 梦鱼币数字”作为奖励唯一事实来源。

建议服务端存在独立、可审计的：

```text
CommissionRewardRecord
```

至少关联：

```text
rewardRecordId
playerUuid
commissionId
batchId
templateId
requesterId
rewardSnapshot
createdAt
mailId
claimStatus
claimedAt
```

建议状态：

```text
PENDING_MAIL
MAIL_CREATED
CLAIMED
FAILED
```

如果未来存在重新投递 / 修复，还可以增加恢复状态。

这样可以解决：

- 邮件创建成功但服务端中途异常；
- 网络断开；
- 重复生成奖励邮件；
- 重复领取；
- 管理员排查某个委托奖励是否已经领取；
- 邮件数据损坏时根据奖励记录恢复；
- 经济审计。

`rewardRecordId` 应成为幂等键之一。

---

# 六、委托完成与奖励到账的状态必须分开

`CommissionInstance` 不应把“已完成”和“钱已到账”视为同一个状态。

建议至少能表达：

```text
任务状态：COMPLETED
奖励状态：MAIL_PENDING / MAIL_SENT / CLAIMED
```

玩家完成任务的一刻，任务本身已经完成，不应因为玩家还没打开邮箱而变回可完成状态。

因此流程是：

```text
完成条件达成
   ↓
Commission = COMPLETED
   ↓
冻结本次 RewardRecord
   ↓
创建奖励邮件
   ↓
Reward = MAIL_SENT
   ↓
玩家领取
   ↓
Reward = CLAIMED
```

这样即使玩家数天不领取邮件，也不会再次完成同一条委托。

---

# 七、公共物资委托的特殊处理

公共物资委托允许部分提交，因此不能把“每交 1 个物品”都生成一封奖励邮件，否则会制造严重邮件垃圾。

建议以**一次玩家主动确认提交**为最小结算单位。

例如玩家一次提交：

```text
铁锭 ×32
预计奖励：288 梦鱼币
```

确认后：

```text
扣除铁锭 ×32
   ↓
减少公共剩余需求 32
   ↓
生成一条贡献结算记录
   ↓
发送一封奖励邮件
```

而不是发送 32 封邮件。

### 可选的后续优化：同委托奖励合并

如果实际服务器测试发现公共委托仍然造成大量邮件，可以进一步支持：

```text
同一 commissionId
+ 同一 playerUuid
+ 未领取
```

的奖励合并到同一封“委托结算邮件”中。

例如玩家先后提交：

```text
32 铁锭 -> 288
64 铁锭 -> 576
```

若前一封仍未领取，可合并为：

```text
城镇建设局 · 铁锭采购结算

本期累计提交：96
待领取：864 梦鱼币
```

但**第一版可以先采用“一次提交一封邮件”**，实现更简单；是否合并根据实际邮件量再决定。

---

# 八、奖励邮件内容设计

奖励邮件不能只是：

```text
系统
你获得了 1260 梦鱼币。
```

应该利用委托人信息增强沉浸感。

例如：

```text
发件人：城镇铁匠铺
主题：矿产采购委托结算

你送来的铁锭已经验收完毕。
按照约定，这是本次委托的报酬。

委托：铁锭采购
提交：160 个铁锭
报酬：1260 梦鱼币
```

附件：

```text
[ 梦鱼币 ×1260 ]
        [领取]
```

猎杀任务例如：

```text
发件人：猎人协会
主题：悬赏完成确认

目标已经确认清除。
这是协会承诺的悬赏金。

目标：僵尸 ×20
报酬：350 梦鱼币
```

这样 `CommissionRequester` 可以进一步承担：

- 邮件发件人名称；
- 邮件签名；
- 不同风格的结算文本；
- 后续头像 / 图标；
- 特殊委托人的特殊措辞。

建议委托模板支持奖励邮件文本变量：

```text
{requester}
{commission}
{item}
{count}
{reward}
{contribution}
{completedAt}
```

---

# 九、完成时的 UI 反馈

委托完成后，委托中心不要出现：

```text
[领取 1260 梦鱼币]
```

而应显示：

```text
✓ 委托已完成
奖励已发送至邮箱
```

可以配合当前邮箱已有的新邮件 Toast / 提示音。

推荐体验：

```text
玩家完成委托
    ↓
委托卡片变为“已完成”
    ↓
右上角出现新邮件通知
    ↓
“城镇铁匠铺向你发送了一封邮件”
    ↓
玩家进入邮箱领取奖励
```

这样能自然把委托系统和邮箱系统串成一条完整体验，而不是两个互相独立的页面。

---

# 十、离线玩家

奖励邮件必须天然支持离线玩家。

例如公共委托阶段奖励或全服完成奖励触发时，玩家不在线：

```text
生成 CommissionRewardRecord
   ↓
持久化奖励邮件
   ↓
玩家下次上线
   ↓
收到新邮件提示
   ↓
正常领取
```

不得因为玩家不在线而：

- 丢失奖励；
- 直接跳过邮箱；
- 下次上线重复生成。

---

# 十一、邮箱容量与奖励可靠性

这是必须单独处理的边界。

玩家可能已经把普通邮箱占满，但完成委托后的奖励不能因为“邮箱满了”直接消失，也不能因为邮件创建失败导致任务可重复完成。

建议将系统奖励邮件与普通玩家邮件的容量策略区分开。

可采用以下一种或组合方案：

1. **系统奖励邮件拥有独立保留容量**；
2. 系统奖励邮件不占普通玩家互发邮件额度，但受独立的较高安全上限约束；
3. 达到安全上限后，对同类未领取奖励进行聚合，而不是删除奖励；
4. 最坏情况下保留 `CommissionRewardRecord`，待邮箱有可用空间时重新投递。

必须满足：

> 邮箱容量限制可以阻止普通玩家把邮箱当无限背包，但不能吞掉已经合法获得的系统奖励。

同时也不能简单让系统奖励邮件无限制永久增长，否则会制造新的持久化膨胀问题。

第一版推荐：

```text
普通个人邮件容量
        与
系统奖励邮件保留额度
```

分离管理，并为未领取奖励保留可恢复的 RewardRecord。

---

# 十二、奖励邮件删除规则

带有未领取奖励附件的邮件不得直接删除。

沿用并强化当前邮箱已有的“有附件邮件不能删除”原则。

只有在：

```text
所有奖励附件已领取
```

之后，邮件才允许普通删除。

如果未来支持“拒绝 / 放弃奖励”，必须做成明确的二次确认行为，不应与普通删除混为一谈。

默认不建议第一版提供“放弃奖励”。

---

# 十三、奖励领取后的经济流水

梦鱼币真正进入账户的时间点是：

```text
玩家领取 CurrencyAttachment
```

而不是：

```text
任务完成
```

因此 Economy Ledger 的实际余额变更记录应发生在领取时。

建议来源：

```text
economysystem:commission_reward_claim
```

同时 CommissionRewardRecord 记录：

```text
commission completedAt
mail createdAt
reward claimedAt
```

这样管理员可以区分：

- 玩家什么时候完成任务；
- 奖励什么时候进入邮箱；
- 玩家什么时候真正领取并造成货币注入。

这对分析服务器实际货币流速很有价值。

---

# 十四、原子性与故障恢复

任务完成、物品扣除、奖励记录和奖励邮件创建必须以事务 / 可恢复流程组织。

以物资提交为例：

```text
验证 Commission
   ↓
验证玩家物品
   ↓
确定实际提交数量和冻结奖励
   ↓
扣除物品
   ↓
更新委托贡献 / 剩余需求
   ↓
创建 CommissionRewardRecord
   ↓
创建奖励邮件
   ↓
提交成功
```

需要避免：

```text
物品扣除了
但 RewardRecord 和邮件都没有
```

以及：

```text
RewardRecord / 邮件重复创建
导致奖励领取两次
```

如果现有基础设施无法真正进行跨存储原子提交，则必须通过：

- 幂等 rewardRecordId；
- 明确状态机；
- 回滚；
- 重试；
- 启动时恢复未完成状态；

实现最终一致性。

客户端永远不能决定奖励金额或邮件是否已经领取。

---

# 十五、与未来玩法的统一

这套“奖励 -> 邮箱”的机制未来不应只服务 Commission。

可以逐步抽象为 EconomySystem 的统一奖励投递能力，例如：

```text
RewardDeliveryService
```

统一接受：

```text
recipient
source
subject
body
currencyRewards
itemRewards
idempotencyKey
```

未来：

```text
委托
探索
活动
职业
管理员补偿
服务器里程碑
```

都可以通过同一奖励投递服务进入邮箱。

这样邮箱会真正成为 EconomySystem 的统一奖励中心。

但市场成交、转账、回收等交易结算仍使用各自事务，不强行邮件化。

---

# 十六、对主委托计划的实施调整

`earning-paths-and-dynamic-jobs-plan.md` 中原先出现的“直接发放梦鱼币 / 即时结算”语义，在 Commission 奖励场景下应解释为：

```text
即时确定奖励并创建奖励邮件
```

而不是直接增加余额。

例如公共物资委托：

原语义：

```text
提交 32 铁锭
-> 立即到账 288 梦鱼币
```

调整为：

```text
提交 32 铁锭
-> 立即生成 288 梦鱼币奖励结算
-> 奖励邮件进入邮箱
-> 玩家在邮箱领取后到账
```

个人猎杀委托：

```text
击杀 20 / 20
-> Commission 完成
-> 生成奖励邮件
-> 邮箱领取
```

公共阶段 / 最终奖励同理。

---

# 十七、第一阶段新增实现要求

在开始实现物资委托 MVP 前，必须先确认邮箱层具备或补齐：

1. 货币奖励附件；
2. 服务端权威领取；
3. 幂等领取；
4. 奖励邮件不能在附件未领取时删除；
5. 离线持久化；
6. 系统奖励邮件容量策略；
7. `CommissionRewardRecord` 或等价可靠结算记录；
8. 新邮件 Toast / 声音复用；
9. Economy Ledger 在实际领取时记账；
10. 奖励投递失败的恢复 / 重试路径。

因此委托实现顺序建议调整为：

```text
Commission Core
      ↓
Mailbox Currency Reward Attachment
      ↓
RewardDelivery / RewardRecord
      ↓
ITEM_DELIVERY Commission
      ↓
ENTITY_KILL Commission
```

---

# 十八、当前补充决策摘要

1. **所有 Commission 奖励禁止直接到账。**
2. **所有 Commission 奖励通过系统奖励邮件投递。**
3. 玩家必须在邮箱中领取货币 / 物品奖励附件后，奖励才真正进入账户或背包。
4. 委托中心只显示“完成、奖励已发送至邮箱”，不提供直接领取按钮。
5. 邮件内容应尽可能使用 `CommissionRequester` 作为发件人并生成具有世界观感的结算文本。
6. 邮箱需要新增或正式抽象货币奖励附件能力。
7. 任务完成状态与奖励领取状态必须分离。
8. 使用独立 `CommissionRewardRecord` 或等价结构保证幂等、审计和故障恢复。
9. 公共物资委托以“一次确认提交”为最小奖励邮件单位，禁止按每个物品发送邮件。
10. 系统奖励邮件容量必须与普通玩家邮件容量策略区分，不能因邮箱满吞掉合法奖励。
11. 未领取奖励附件的邮件不得普通删除。
12. Economy Ledger 在玩家真正领取货币附件时记录余额变动。
13. 离线玩家照常收到持久化奖励邮件。
14. 未来探索、职业、活动、剧情等“奖励型玩法”统一复用同一奖励投递路径。
15. 回收站、市场、转账等“交易型收入”默认仍即时结算，不强制通过邮箱。
